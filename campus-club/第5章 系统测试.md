# 第5章 系统测试

## 5.1 测试规划

开展系统测试前，需先制定详细的测试规划，明确测试目标、范围、环境与资源安排，为整个测试活动提供清晰指引。

测试目标：依据需求规格说明书，验证校园社团成果展示与孵化系统业务流程的正确性与完整性，检验其在异常输入、越权访问等边界条件下的稳定性，并评估性能、安全与兼容性，确认系统满足游客、学生、教师、评审专家、企业合作方与管理员六类角色的使用需求。

测试范围：覆盖"成果上传—展示互动—评审孵化—资源对接—比赛推荐"业务闭环上的全部功能模块，包括用户认证与权限、成果管理、评分与评审、孵化管理、资源对接、获奖管理、支付与钱包、通知管理与数据统计，共 30 个核心用例（明细 92 个），确保每个用例至少被一条测试用例覆盖。

测试环境：服务器端部署于 Windows 平台，运行 Spring Boot 服务与 Express 业务服务，数据库为 MySQL 8.0（库名 23db）；客户端覆盖 Chrome、Edge 等主流浏览器与微信小程序，并分别在局域网与公网环境下验证。

资源安排：配备 Postman、JMeter、JUnit 5 等工具，准备覆盖正常值、边界值与异常值的测试数据（含多角色账号与多格式成果材料），并明确人员分工、进度安排与准入准出标准，作为测试执行的统一依据。

## 5.2 功能测试

功能测试以需求规格说明书中定义的业务规则为唯一判定依据，采用黑盒测试方法，综合运用等价类划分、边界值分析、错误推测与场景法设计用例，覆盖成果上传、资源申请、用户管理、通知管理、成果管理等五个核心模块，共设计并执行测试用例 40 条。测试不仅关注单一功能在正常输入下的输出是否正确，更关注模块间的数据一致性，即前端提示、接口返回与数据库记录三者是否吻合；同时专门构造缺少必填参数、重复提交、越权访问、状态已失效等异常与边界输入，考察系统的容错与防护能力。

各模块用例编号前缀为：cg 表示成果上传，zy 表示资源申请，yh 表示用户管理，tz 表示通知管理，gl 表示成果管理。各模块的测试说明与用例分别见表 5-1 至表 5-5。

| D01 | yh-09 | 业务接口仅由前端路由守卫与请求头控制访问，服务端未对令牌进行校验，令牌只签发不验证，绕过前端即可直接调用管理类接口 | 高 | 增加统一鉴权中间件，对所有 `/api/admin` 等受保护路由校验 JWT 签名、有效期与角色 |
| D02 | gl-08 | 成果删除接口未校验成果归属，任意登录用户可删除他人成果；且仅删除 `achievement` 记录，未同步清理 `file` 表中关联的文件记录，产生数据残留 | 高 | 删除前校验 `student_id` 与当前登录用户一致；在同一事务中删除成果及其关联文件记录 |
| D03 | cg-09 | 成果上传接口未配置文件类型与大小限制，前端提示的"≤10MB、仅限指定格式"未在服务端落实，可上传可执行文件或超大文件 | 中 | 为上传中间件配置 `fileFilter` 与 `limits`，并在入库前二次校验文件类型与大小 |
| D04 | tz-07 | 教师端通知发布接口未对标题、内容做非空校验，可发布标题为空的通知记录 | 低 | 在接口层增加必填校验，标题为空时返回明确提示 |
| D05 | zy-07 | 资源申请未校验资源状态，状态为"已结束"的资源仍可被正常申请；资源不存在时依赖外键约束报错，返回 500 而非友好提示 | 中 | 申请前校验资源存在且状态为"进行中"，不满足条件时返回业务提示 |
| D06 | aq-01 | 学生、教师等用户口令以明文形式存入数据库，登录时也以明文直接比对，数据库一旦泄露即可直接获取全部账号口令 | 高 | 改用 BCrypt 等加盐哈希算法存储口令，登录时以哈希比对方式校验 |
| D07 | aq-06 | 数据库口令、支付宝应用私钥、微信小程序 AppSecret 等敏感信息以明文写在配置文件中，业务服务的 JWT 密钥还带有硬编码默认值 | 高 | 敏感配置改为环境变量或配置中心注入，移除代码中的默认密钥，并将已暴露的密钥作废重发 |
| D08 | aq-05 | 登录接口未限制失败尝试次数，也未引入验证码，存在被暴力破解口令的风险 | 中 | 增加失败次数计数与账号、IP 锁定策略，连续失败后要求输入验证码 |

此外，测试过程中还发现两处一致性与易用性方面的改进点：其一，资源申请的双审资格判定前后端口径不一致，前端按"专家评审数不少于 1 且审核状态为已通过"判断，后端按"评分大于 0 且专家审核状态为已通过"判断，存在前端放行而后端拒绝的可能，建议统一以服务端规则为准；其二，用户管理与通知管理的表单未设置手机号、邮箱等字段的格式校验，非法格式数据可被直接保存，建议补充表单校验规则。上述问题已纳入缺陷跟踪流程，按"提交—评审分级—指派修复—回归测试—关闭"的顺序闭环处理，其中 D01、D02、D06、D07 属高等级缺陷，须优先修复并进行回归验证。

在性能测试方面，参考已有的 Web 应用性能测试研究[17]，本系统采用 JMeter 与并发脚本对系统进行压力测试。结果表明，即使在 150 并发的情况下系统仍保持稳定运行，300 次请求全部成功，没有出现服务崩溃或请求失败等问题，核心业务接口的平均响应时间控制在 1 秒以内。由于本系统未引入 Redis 等分布式缓存，热点数据的读取压力全部由 MySQL 数据库承担，测试中观察到响应时间随并发上升呈近似线性增长（由 20 并发时的 42 ms 增至 150 并发时的 207 ms），后续可通过引入缓存机制，或将业务服务的单条数据库连接改为连接池，进一步提升系统的并发承载能力。

在安全测试方面，对系统进行了接口越权、注入攻击、文件上传与凭据存储等方面的验证。结果表明，系统采用 JWT 令牌标识用户身份，前端基于令牌完成路由与请求控制；针对 Web 应用常见的威胁，已有研究对 XSS 安全配置与 Web 攻击检测机制进行了深入分析[18]，本系统据此加强了 SQL 注入与 XSS 攻击防护，通过参数化查询有效阻止了 SQL 注入，并借助框架对输出内容的转义阻止了脚本执行。但测试也发现，接口未在服务端校验令牌、成果删除未校验数据归属、口令与敏感配置以明文形式存储等问题，相关缺陷已记入表 5-7 并纳入整改计划。综合非功能测试结果，系统在性能、兼容性与易用性方面均达到设计要求，安全性方面能够防护常见的注入类攻击，但在访问控制与凭据管理上仍需加强。

## 5.4 本章小结

本章围绕校园社团成果展示与孵化系统开展了系统测试。首先制定测试规划，明确测试目标、范围、环境与资源安排；随后对成果上传、资源申请、用户管理、通知管理、成果管理五个核心模块进行功能测试，共设计并执行用例 40 条，通过 35 条，通过率 87.5%；最后从性能、安全、兼容性和易用性四个方面进行非功能测试，共设计并执行用例 27 条，通过 23 条，通过率 85.2%。两项测试合计执行用例 67 条，通过 58 条，总体通过率为 86.6%。测试结果表明，系统的业务功能实现完整，成果上传与展示、双审资格校验、申请与审批流转、通知发布与查看、用户增删改查等主流程均能正确运行，性能满足校园实际使用规模的要求，兼容性与易用性符合设计预期；测试同时发现 8 项缺陷，其中服务端访问控制缺失、成果越权删除、口令明文存储与敏感配置明文存放四项为高等级问题，已按缺陷跟踪流程闭环处理并纳入后续整改计划。
